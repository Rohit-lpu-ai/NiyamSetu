# NiyamSetu backend - Phase 1 (PDF ingestion) + Phase 2 (segmentation)

# Deliberately minimal. Every line is pinned so the five of us run the same
# code. Add a package only with a written justification (CLAUDE.md §24 rule 5),

# Install into a project virtualenv, not globally:
#   python -m venv .venv
#   .venv\Scripts\activate          (Windows)
#   source .venv/bin/activate       (macOS / Linux)
#   pip install -r requirements.txt

# --- runtime: the production extraction path ---
# Pure-Python PDF reading. Gives per-page access, which is what page-level
# provenance depends on, with no compiled extension. This is the library
# `extract_pdf` actually uses, and Experiment A confirmed it should stay the
# default. See docs/pdf-extraction.md and
# evaluation/experiment-a-extractor-comparison.md.
pypdf==6.18.1

# --- evaluation only: Experiment A extractor comparison ---
# Approved by the project owner for the Experiment A comparison
# (CLAUDE.md §15). Imported *lazily*, only by
# backend/app/document_processing/extractor_backends.py, so the production
# ingestion path still runs with pypdf alone and the document_processing
# package stays importable without them.
#
# Cost of these two lines, measured: the virtualenv grows from ~25 MB to
# ~314 MB. PyMuPDF 2.1 is 105 MB on its own and pulls pymupdf-layout,
# pymupdf4llm and onnxruntime (48 MB) as hard dependencies; pdfplumber pulls
# pdfminer.six, Pillow and pypdfium2. That footprint is recorded here because
# it is the main argument against making either one the default extractor for a
# five-machine student project.
#
# Experiment A's verdict (see the report): pypdf stays the default page-text
# extractor; PyMuPDF is retained for its table API, which is the one capability
# pypdf genuinely lacks.
pymupdf==2.1
pdfplumber==0.11.10

# --- development / test ---
pytest==8.3.4

# --- NOT dependencies of this phase ---
